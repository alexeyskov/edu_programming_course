# Аудит старого прототипа и реализуемость

## 1. Что было просмотрено

Старая версия в `_old_cpp_course_automatization` содержит:

- монолитный FastAPI backend объёмом более четырёх тысяч строк;
- монолитный Vue-компонент преподавательского интерфейса сопоставимого размера;
- PostgreSQL-таблицы `students`, `tasks` и набор добавочных `app_*`;
- Selenium-парсер Moodle и по одному Chrome WebDriver на активную Moodle-сессию;
- скрипты скачивания вложений, разворачивания локальных include, объединения проекта в один `.cpp` и запуска `g++`;
- LLM-проверку через OpenAI-compatible API, генерацию тестового harness и диагностики по строкам;
- токенизированный winnowing/fingerprint-анализ плагиата;
- присутствие преподавателей на задаче, ручное применение оценки в Moodle и фоновые задания;
- Monaco в режиме просмотра/песочницы;
- Ollama/vLLM/OpenRouter-эксперименты и исследовательские ноутбуки.

Код старой версии не должен импортироваться в новую. Допустимо перенести только сформулированные требования и тестовые примеры после отдельной проверки лицензий и качества.

## 2. Полезные продуктовые идеи

- ИИ создаёт рекомендацию, Moodle изменяется только после действия преподавателя.
- Присутствие другого проверяющего видно рядом с задачей.
- Компиляторные и модельные диагностики привязаны к строкам.
- Плагиат показывает пару решений и совпавшие фрагменты, а не только число.
- Есть отдельная временная песочница преподавателя, не меняющая сдачу.
- Фоновый импорт и восстановление файлов имеют наблюдаемый прогресс.
- Учитываются inline-ответы Moodle Essay и файловые ответы Assignment.
- Обработка больших файлов ограничивает нагрузку на Monaco.
- Попытки группируются в работу, а оценка масштабируется к максимальному баллу.

Эти идеи отражены в новой спецификации, но реализуются заново.

## 3. Критические архитектурные проблемы прототипа

### 3.1. Запуск непроверенного кода

`g++` и получившийся бинарник запускаются непосредственно процессами backend-хоста и имеют обычный обзор его файловой системы. Это не выполняет даже обновлённую облегчённую политику: student process должен видеть только текущий job и разрешённый read-only toolchain/runtime.

Новая версия не требует gVisor/microVM как обязательного условия. Достаточен отдельный непривилегированный runner-процесс или rootless container с mount/filesystem namespace, одноразовым каталогом и очищенным environment. Если он разделяет kernel/host с основным приложением, риск syscall/kernel escape сознательно остаётся; прямой `subprocess` из web worker всё равно запрещён.

### 3.2. Распаковка и файловая система

ZIP/7z/RAR обрабатываются в серверной файловой системе, а часть путей жёстко задана. Использование небезопасного извлечения архивов создаёт риск выхода файла за временный каталог. В новой системе пути нормализуются, симлинки запрещаются, архивы анализируются только в private workspace отдельного runner job, а результат копируется через контролируемый API.

### 3.3. Moodle через браузер

На вход каждого преподавателя создаётся WebDriver, пароль вводится в Moodle через Selenium, а cookies копируются в `requests.Session`. Это имеет следующие последствия:

- Chrome потребляет значительную память на пользователя;
- состояние хранится в памяти одного процесса и теряется при рестарте;
- блокировки действуют только внутри процесса;
- горизонтальное масштабирование не работает без sticky sessions;
- CSS-селекторы и ручные URL зависят от темы и версии Moodle;
- массовый вход выглядит как автоматизированный трафик и усложняет аудит;
- обновление Moodle может незаметно сломать выставление оценок.

Playwright contexts дешевле отдельных браузеров, но не исправляют зависимость от HTML, CSRF, пользовательских cookies и изменений интерфейса. Поэтому Playwright пригоден для E2E-тестов и временного миграционного fallback, но не для штатной синхронизации.

### 3.4. Аутентификация

Прототип сочетает общий ручной access token, токен Moodle-сессии и хранение обоих секретов в `localStorage`. Общий access token защищает весь API одинаково и не подтверждает личность или область доступа.

В новой системе нет локальной регистрации и локальных ролей: личность и только
`STUDENT`/`TEACHER` подтверждает LMS-коннектор, после чего core выдаёт серверную
`HttpOnly Secure SameSite` session cookie. Требуемое поле «Токен
администратора» имеет принципиально другую семантику: оно может лишь повысить
уже внешне аутентифицированную сессию для глобальных настроек и не отправляется
как bearer header каждого запроса. Для удобства пилота административный и
преподавательский токены сохраняются origin-scoped в browser `localStorage`,
отображаются только как password-поля и могут быть удалены пользователем.
Moodle-пароль, cookies и серверный browser state в это хранилище не попадают.

### 3.5. Монолит и фоновые потоки

API, scheduler, Selenium, компиляция, LLM, плагиат, удаление файлов и интерактивные процессы находятся в одном модуле. Фоновые бесконечные потоки стартуют вместе с web-процессом. При нескольких worker-процессах задания дублируются, а глобальные словари сессий расходятся. Новая система использует транзакционную очередь, outbox и отдельные worker-процессы.

### 3.6. Модель данных

Студент идентифицируется преимущественно ФИО, курс — числом, тип работы угадывается по названию, а внешние связи часто лежат в `raw JSON`. Это не выдерживает смены имени, одинаковых ФИО, нескольких LMS installations, повторного курса или конфликта синхронизации. Требуются стабильные внешние ID, scoped memberships, версионирование и таблица mappings.

### 3.7. Импорт по URL — не импорт курса

Старая UI принимает отдельную ссылку на страницу участников и отдельные ссылки Moodle Assignment/Quiz, затем парсит HTML и сохраняет import jobs. Это полезно как подтверждение востребованности URL-driven workflow, но не реализует новое требование «добавить курс одной ссылкой»: нет единого course discovery, capability report, проверки внешней роли для стабильного course ID и абстракции другой LMS.

В новой системе остаётся удобство одной ссылки, но меняется механизм: URL распознаёт конкретный connector, затем данные читаются через LTI/API/bridge. Старые selectors и parser functions не переносятся.

### 3.8. Тестируемость и эксплуатация

Для прикладной части практически нет автоматических тестов, миграции смешаны с `CREATE TABLE IF NOT EXISTS`, CORS разрешён для всех источников, настройки и сетевые адреса жёстко заданы. Нет единого аудита, секрет-хранилища, метрик SLO и процедуры disaster recovery.

## 4. Оценка реализуемости

| Возможность | Оценка | Условие/ограничение |
| --- | --- | --- |
| Браузерная C/C++ IDE | реализуемо | Monaco; сложность растёт с clangd и multi-file |
| Одно- и многофайловая сборка | реализуемо | фиксированный build profile, без произвольного CMake в первой версии |
| Запрет внешней вставки | реализуемо как барьер | обходится DevTools, автоматизацией ввода и перепечатыванием |
| История до отдельных операций | реализуемо | batching, sequence/hash chain, snapshots и нагрузочное тестирование |
| Внешний анализ авторства | реализуемо | только вероятностный сигнал, нужен версионированный API |
| Облегчённый запуск C++ | реализуемо | отдельный unprivileged job, allow-listed read-only toolchain, private writable workspace; kernel/network risk принимается |
| Полуавтоматическая проверка | реализуемо | детерминированные проверки первичны, преподаватель финален |
| Плагиат с фрагментами | реализуемо | исключение шаблонного кода, калибровка и ручное решение |
| Студенческий ИИ без готового кода | частично контролируемо | многоуровневая политика снижает риск, но абсолютной гарантии нет |
| Чат преподавателя | реализуемо | хранение собственных разговоров, provider abstraction |
| Проверка без дублей | реализуемо | распределённый lease и optimistic concurrency |
| Внешний вход, две роли, оценки и состав | реализуемо | общий connector contract; для Moodle — LTI 1.3/bridge и разрешения администратора сайта |
| Добавление курса одной ссылкой | реализуемо | URL — только locator; discovery через API/bridge, проверка teacher membership и защита от SSRF |
| Общий административный токен | реализуемо, но рискованно | только step-up после LMS-входа, hash/rotation/rate limit/audit; позднее индивидуальное MFA |
| Полная двусторонняя синхронизация банка | сложно, но реализуемо | Moodle bridge + mapping + conflict UI; core API недостаточно |
| Надёжная синхронизация без доступа администратора Moodle | проблематично | только хрупкий браузерный fallback с урезанными гарантиями |
| Доказательство, что код написал именно студент | невозможно гарантировать | история и анализ дают свидетельства, не доказательство личности |

## 5. Что сознательно не переносится

- объединение любого проекта в одну translation unit как основной способ multi-file;
- прямой `subprocess` на сервере приложения;
- WebDriver на пользователя;
- общий access token;
- идентификация по ФИО;
- фоновые daemon threads в web-процессе;
- запись бинарников и ответов в случайные каталоги на локальном диске приложения;
- LLM-текст с оценкой, извлекаемой регулярным выражением как единственный контракт;
- embedding как первичный вердикт плагиата;
- CORS `*` с учётными данными;
- изменение таблиц при старте приложения вместо миграций.

## 6. Итог аудита

Прототип доказал полезность преподавательского интерфейса и отдельных алгоритмических идей, но не является безопасной или масштабируемой основой. Оптимальная стратегия — clean-room реализация с переносом требований, тестовых наборов и измеримых критериев, а не модификация существующего приложения.
