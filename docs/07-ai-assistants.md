# ИИ-ассистенты

> Статус baseline v1: persistent student/teacher threads, global/course flags,
> bounded context/history, Responses, Chat Completions и Ollama adapters, mock provider,
> student input/output regex gates и allow-list только `cppreference.com`
> реализованы. Server-side rate budget до provider call также реализован:
> 10 student- и 30 teacher-сообщений на пользователя/режим за 60 секунд по
> умолчанию, суммарно по threads. Рекомендательный анализ immutable-сдач с
> отдельной административной настройкой работы, очередью, замечаниями по строкам
> и отдельной рекомендацией балла/комментария реализован. Retrieval index/tools,
> денежный/token budget accounting, moderation pipeline и
> полный eval set ниже ещё не готовы.

## 1. Роль ИИ

В системе есть три разных режима, которые нельзя объединять одним prompt:

1. **Студенческий tutor** — помогает понять, но не решает за студента.
2. **Преподавательский review chat** — подробно анализирует сдачу по запросу преподавателя.
3. **Фоновая СППР** — формирует структурированную предварительную рекомендацию.

У каждого режима свой policy, tools, retention, model budget и набор доступных данных.

## 2. Provider abstraction

Core interface должен поддерживать:

- OpenAI Responses API;
- локальную модель через внутренний provider service;
- OpenAI-compatible provider только через отдельный адаптер;
- mock/replay provider для тестов.

Стандартный профиль подключения — `AI_API_STYLE=chat_completions`,
`LLM_API_ADDRESS=https://llm.example.org/v1`, `LLM_MODEL` с именем развёрнутой
модели и необязательный `LLM_API_KEY`. Ollama, vLLM и SGLang подключаются одним
адаптером: `POST /v1/chat/completions` с `model`, `messages`. Обычные запросы
используют `stream=false` и `choices[0].message.content`; чат преподавателя —
`stream=true` и SSE `choices[0].delta.content`. Ключ передаётся как Bearer.
Для переносимости `LLM_THINKING` оставляется пустым: нестандартные для сервера
настройки reasoning не добавляются. Адрес может содержать prefix reverse proxy
или полный `/chat/completions`; суффикс не дублируется.

Текущий adapter также сохраняет OpenAI Responses и родной Ollama `/api/chat`
для существующих конфигураций. Настройки `LLM_API_ADDRESS`,
`LLM_MODEL` приоритетнее старых `AI_*`. Ключ выбирается как первое непустое
значение `LLM_API_KEY` → `OPENROUTER_API_KEY` → `AI_API_KEY`; launcher также
может прочитать буквальное присваивание OpenRouter-ключа из `.bashrc` пользователя
сервиса, без выполнения файла. Для локальной Ollama ключ не требуется:
оставьте все три переменные пустыми, включая `OPENROUTER_API_KEY`, чтобы запретить
его загрузку из профиля. Явный `LLM_THINKING=0/1` передаётся как `think` в родном API Ollama,
`reasoning.enabled` в OpenRouter, `reasoning_effort` в Chat Completions и
`reasoning.effort` в Responses. Отсутствующее значение сохраняет настройки
провайдера. Возможность переключения thinking определяется сервером и моделью;
reasoning-поля не показываются как итоговый ответ. Примеры ENV и откат прежней
привязки Ollama к Docker-мосту —
в [инструкции развёртывания](../DEPLOYMENT.md#7-ai-провайдер).

Адаптер не использует provider tools/retrieval и хранит собственные
threads/messages. `store=false`, structured outputs и usage/budget accounting в
baseline payload явно не настраиваются; это нужно согласовать до включения
реального provider.

Provider-specific response IDs не являются доменной моделью chat. Система хранит собственные threads/messages и может отправлять историю stateless. Для OpenAI допустимы conversation/previous response, но при требованиях университета предпочтительно `store=false` и собственное хранение. Официальный Responses API поддерживает instructions, conversation state, structured output, tools и отдельное управление хранением.

Целевой audit каждого вызова должен хранить model ID, provider,
prompt/policy version, input/output hashes, latency, usage, filter outcome и
trace ID. Baseline `ChatMessage` хранит собственный content, citations, model и
safety outcome, а `ChatThread` — policy version/context; provider response IDs,
usage/cost, latency и request/response hashes пока отдельно не сохраняются.

### 2.1. Контекст текущей задачи

Каждый вопрос сопровождается контекстом, заново собранным на сервере:

- условие и название из `TaskVersion`, назначенной именно открытой задаче
  (не последней версии банка и не соседнему вопросу Quiz), язык и его стандарт;
- инструкции работы;
- полный текст всех файлов решения, включая вспомогательные и пустые файлы;
- ограниченная история диалога этой задачи.

Студентский чат сначала дожидается сохранения всех правок IDE и передаёт
подтверждённую ревизию. Сервер проверяет её при каждом сообщении, а не только
при создании чата, и берёт текущие неудалённые файлы workspace. При ошибке
сохранения или конфликте ревизий вопрос с устаревшим кодом не отправляется.
Преподавательский чат берёт файлы из immutable snapshot выбранной сдачи,
не из преподавательской экспериментальной копии или текущего workspace.

В преподавательский контекст входит текущий комментарий формы проверки,
включая несохранённые правки. Это только контекст: чат не сохраняет review draft
и не меняет оценку. Если API-вызов не передаёт комментарий, сервер использует
собственный актуальный черновик преподавателя или последнее применённое решение.
Чужой личный черновик не включается; явная пустая строка означает очищенный
комментарий. Студенческому чату комментарии преподавателя не передаются.

При переключении между задачами интерфейс меняет чат вместе с контекстом и не
показывает запоздалый ответ от предыдущей задачи. По умолчанию поле вопроса пустое.
Действие «Спросить у ИИ» прикрепляет выделенный код или код замечания отдельной
компактной карточкой над полем ввода. Вопрос преподаватель пишет сам; уже набранный
текст не заменяется. У студента этих действий нет.

Контекст не обрезается: если JSON условия и файлов превышает
`AI_MAX_CONTEXT_BYTES` (по умолчанию 256 KiB), сервер возвращает
`413 AI_CONTEXT_TOO_LARGE` до обращения к модели. Администратор может увеличить
лимит с учётом окна контекста используемой модели. Скрытые тесты и эталонные
решения в контекст не включаются. Для старых попыток без назначенной
`TaskVersion` доступен только текст инструкций работы.

## 3. Студенческий tutor

### 3.1. Policy matrix

| Режим | Рекомендуемый default |
| --- | --- |
| Лабораторная | включён: концепции, наводящие вопросы, диагностика причины, документация |
| Самостоятельная | концептуальные объяснения; исправленный код и алгоритм решения запрещены |
| Контрольная | выключен; опционально только поиск по разрешённой документации |
| Экзамен | выключен глобальной политикой |

Глобальный kill switch меняется только в сессии с `SYSTEM_SETTINGS`, полученной после ввода административного токена. Преподаватель настраивает ИИ для своих курсов и конкретных работ в пределах глобальной политики. Это не создаёт отдельные роли администратора курса или организации.

Фактические настройки текущей реализации:

- При первом импорте ИИ включается для работ типа `LAB`; для самостоятельных,
  контрольных и экзаменов — выключается. Тип определяется по названию работы
  и раздела Moodle. Это начальное значение, а не неизменяемый запрет.
- Преподаватель меняет флаг в карточке работы → «Изменить доступ» (для черновика
  «Настроить доступ») → «Разрешить учебного ИИ-помощника». Это локальная настройка:
  в Moodle ничего не записывается, повторная синхронизация выбор не сбрасывает.
- Помощник доступен только при настроенном провайдере, включённых глобальных
  флагах ИИ и студенческого ИИ, разрешении конкретной работы и активной попытке.
  Все проверки выполняются на backend, а не только скрытием кнопки.
- В Quiz с несколькими задачами разрешение берётся у общей работы для каждого
  решения. Контекст помощника содержит код выбранной задачи. Изменение флага
  применяется к уже открытым попыткам; IDE обновляет доступность при опросе.

### 3.2. Разрешённые ответы

- объяснить термин или механизм C++;
- разъяснить текст сообщения компилятора;
- указать область/строку, где искать причину;
- задать наводящий вопрос;
- предложить мысленный тест или контрпример;
- назвать конструкцию языка или идентификатор из кода, без написания примера;
- дать ссылку на документацию и кратко объяснить релевантный раздел;
- объяснить поведение STL container/algorithm.

### 3.3. Запрещённые ответы

- любой сгенерированный код, в том числе короткий пример или отдельная строка;
- патчи, псевдокод и замаскированный/закодированный вариант решения;
- готовая требуемая функция/класс;
- исправленная целиком версия student file;
- пошаговый алгоритм, однозначно превращающийся в ответ контрольной;
- скрытые тесты, эталон или rubric internals;
- оценка вероятности плагиата/авторства;
- обход paste/timer/exam controls.

## 4. Многоуровневое ограничение выдачи кода

Prompt недостаточен. Нужны слои:

1. Входной classifier определяет intent: concept, error explanation, solution request, policy bypass.
2. Context builder передаёт весь код только открытой задачи и отделяет его как untrusted data.
3. Tool allow-list: только retrieval по разрешённым источникам; без shell и произвольного web.
4. System policy запрещает готовое решение и скрытые данные.
5. Structured response содержит answer, hints, citations, policy flags.
6. Output gate ищет code fences, высокую плотность C++ tokens, целые функции/classes и сходство с task statement/reference.
7. При нарушении ответ блокируется и перегенерируется в более абстрактной форме.
8. Rate/turn/token limits мешают собрать решение по частям.
9. Все assessed-chat turns доступны преподавателю и audit согласно политике.
10. Набор jailbreak/prompt-injection evals выполняется на каждой версии policy/model.

Даже эти меры снижают, но не исключают утечку решения. Для экзамена безопасный default — отсутствие генеративного tutor.

Текущая политика `student-no-code-v2` разрешает только текстовые объяснения,
наводящие вопросы и ссылки на документацию. Перед возвратом ответа сервер
отклоняет любые fenced-блоки (даже короче 80 символов), функции и характерные
операторы C/C++; отклонённый код не возвращается студенту и не сохраняется как
ответ чата. Имена файлов, номера строк и названия конструкций допустимы.
Текст задания, исходники и комментарии обозначаются как данные, а не инструкции
для модели. Regex gate не является полным семантическим классификатором:
нельзя гарантировать распознавание любого замаскированного решения.

Пункт 8 частично работает уже в baseline: до обращения к provider backend под
блокировкой principal row считает `USER` messages владельца во всех threads
текущего режима за `AI_RATE_LIMIT_WINDOW_SECONDS`. Defaults —
`AI_STUDENT_RATE_LIMIT_MESSAGES=10` и
`AI_TEACHER_RATE_LIMIT_MESSAGES=30` за 60 секунд. Превышение возвращает
`429 AI_RATE_LIMIT` с limit/window и не вызывает provider. Это rate control, а
не учёт токенов, денег или месячного бюджета курса.

## 5. Документация и citations

Retrieval index должен включать только разрешённые источники:

- материалы конкретного курса;
- [cppreference](https://en.cppreference.com/w/) как практический справочник;
- публичный draft стандарта C++, если преподаватель считает нужным;
- официальную документацию GCC/Clang;
- локальные методические материалы.

cppreference полезен, но не является нормативным текстом стандарта. UI показывает title, URL, section/anchor и retrieval timestamp. Ответ без найденного источника должен честно обозначать, что citation не найден, а не создавать ссылку.

Индекс хранит license/provenance metadata; нельзя автоматически копировать и раздавать большие фрагменты сторонней документации.

В baseline retrieval index отсутствует: provider answer обязан содержать
allowlisted HTTPS citation под `/w/` доменов cppreference; student answer без неё
отклоняется. Локальные policy-refusal ответы `BLOCKED_INPUT`/`BLOCKED_SOLUTION`
не являются provider answer и намеренно могут не иметь citation.
GCC/Clang/course-doc citations пока не разрешены adapter-ом, несмотря
на целевой список выше.

## 6. Лабораторное мини-окно

- открывается поверх IDE и привязано к attempt/task;
- диалог привязан к открытой задаче, закрытие панели в той же задаче его не сбрасывает;
- условие и все файлы решения прикладываются автоматически к каждому вопросу;
- модель видит подтверждённую сервером workspace revision;
- UI показывает, что ответ может ошибаться;
- при закрытии dialog не переносит скрытую память в следующую работу;
- «временный» означает отсутствие пользовательского long-term memory. Audit retention задаётся политикой и отображается до первого сообщения.

Рекомендуемый retention: лабораторные turns 30 дней, assessed turns до завершения апелляции, преподавательские threads до явного удаления/архива курса. Университет должен утвердить сроки.

Автоматического retention cleanup baseline не содержит; рекомендации выше не
следует трактовать как действующую политику удаления.

### 6.1. Ручная очистка закрытых переписок

В настройках администратора есть отдельный блок «Очистка переписок с ИИ».
Он показывает число доступных для удаления чатов преподавателей, студентов
и сообщений. Перед удалением счётчики обновляются и требуется подтверждение.
Очистка не привязана к кнопке сохранения общих настроек и сама по расписанию не запускается.

`GET /system/ai-chat-cleanup` возвращает только агрегированные счётчики и временную
границу. `POST` на тот же адрес требует `confirm: true`, `closed_before` из
предпросмотра, CSRF и действующую capability `SYSTEM_SETTINGS`. Удаляются
только `CLOSED` threads режимов `TEACHER` и `STUDENT` вместе с их `ChatMessage`.
Переписки, закрытые после предпросмотра, в подтверждённую очистку не попадают.
Операция атомарная; повтор с той же границей безопасен и возвращает фактические
счётчики. Чаты, занятые другим запросом, пропускаются до следующей очистки.

Действующие чаты, результаты рекомендательного анализа работ, оценки,
исходники и история редактирования не удаляются. Для защиты выполняющихся
запросов и лимитов сообщений выдерживается интервал после закрытия чата
и последнего сообщения: максимум из 5 минут, `AI_TIMEOUT_SECONDS + 5` секунд
и `AI_RATE_LIMIT_WINDOW_SECONDS`. Очистка удаляет записи из текущей базы,
не переписывая резервные копии; восстановить переписки через интерфейс нельзя.
В аудит сохраняется `ai_chats.cleaned_up` с инициатором, границей и количеством
удалённых чатов/сообщений — без содержимого переписок. Изменение схемы БД для
этой функции не требуется.

## 7. Преподавательский review chat

Реализованный автоматический контекст описан в разделе 2.1: условие выбранной
задачи, полный immutable submission snapshot, комментарий преподавателя и
история её чата. Вручную прикреплять код или выбирать его фрагмент не требуется.

Дополнительный контекст для дальнейшего развития (пока не прикладывается автоматически):

- rubric;
- compile/test/sanitizer evidence;
- selected diagnostics и code ranges;
- разрешённая C++ документация.

Функции:

- спросить о конкретной ошибке/undefined behavior;
- сопоставить код с критерием рубрики;
- объяснить падение теста;
- предложить дополнительные проверочные случаи;
- сравнить два teacher-selected fragments;
- сформулировать черновик комментария.

Чат может предложить код для эксперимента преподавателя, но вставка требует явного действия и попадает только в `teacher_experiment`. Такой код компилируется/запускается тем же file-isolated runner и никогда не меняет submission. Ответы цитируют file hash/line range и evidence IDs.

## 8. Фоновая СППР

Администратор управляет `Assessment.ai_review_enabled` в карточке конкретной
работы. Для новых работ, включая впервые импортированные из Moodle, проверка
включена по умолчанию. Миграция `20261019_0027` меняет только значение по умолчанию:
сохранённые настройки существующих работ (в том числе отключение) не меняются,
массовая постановка старых сдач в очередь не выполняется. Повторная синхронизация
Moodle также сохраняет выбранную настройку. Это отдельное разрешение:
`student_ai_enabled`, `teacher_ai_enabled` и старый
`decision_support_enabled` не изменяются и не блокируют новый режим. Глобальный
`ai_enabled` и наличие настроенного провайдера остаются обязательными.

После сдачи студентом или импорта сдачи из Moodle в той же транзакции создаётся
`AICodeReview` со статусом `QUEUED`. При включении настройки добавляются также
имеющиеся непроверенные сдачи выбранной работы; утверждённые результаты не
перепроверяются автоматически. Каждая задача многовопросного Quiz использует
настройку родительской работы, но собственное условие и собственный снимок кода.

При импорте сначала сохраняется проверка Moodle, затем решается вопрос о запуске
ИИ. Балл `0` и комментарий преподавателя без числовой оценки тоже запрещают
автоматическую проверку. Комментарий без балла показывается отдельно, оценка
не придумывается. Учитывается и Moodle-копия той же локальной попытки/задачи;
чужие студенты, курсы и попытки не смешиваются. Worker повторяет эту проверку
перед вызовом модели: уже поставленная автоматическая задача становится
`SKIPPED`, если появился результат преподавателя. Ручной запуск по-прежнему
разрешён и в этом случае, и для ранее оценённых работ.

Повторная синхронизация обновляет импортированное решение из Moodle; изменение
в Moodle после доставленной локальной оценки также становится основным решением.
Предыдущая оценка остаётся в истории. Явно утверждённое локальное решение, ещё
ожидающее отправки (включая ошибку отправки), не затирается устаревшим read-back.
Ошибка авторизации Moodle не означает отсутствия проверки: нужно заново войти
в Практикум через Moodle и повторить синхронизацию, а не использовать ИИ как замену
неудавшемуся импорту.

Отдельный последовательный worker при API lifespan обрабатывает очередь,
не задерживая отправку студента или синхронизацию Moodle. Состояния:
`QUEUED → RUNNING → COMPLETED | QUEUED (повтор) | FAILED`. На один запуск
разрешено не более трёх обращений к модели: первая попытка и два повтора.
При ошибке ответа или транспорта повторы выполняются после пауз 2 и 4 секунды,
каждый запрос сохраняет лимит 180 секунд по умолчанию. Счётчик `attempt_count`
и время `next_attempt_at` хранятся в базе (миграция `20261005_0026`), поэтому
рестарт или обновление страницы не сбрасывают бюджет. Зависший `RUNNING`
повторяется только в пределах оставшегося бюджета; после третьей ошибки —
`FAILED`. Успех останавливает повторы. При
глобальном отключении или отсутствии провайдера очередь ждёт без внешних
вызовов. Результат привязан к `submission_id + snapshot_id + manifest_hash`;
смена снимка при импорте делает старую задачу неактуальной.

API:

- `PATCH /assessments/{id}/ai-review-policy` с `{enabled: bool}` — только
  `SYSTEM_SETTINGS`, работает и для опубликованных/завершённых заданий;
- `GET /ai/submissions/{id}/code-review` — состояние и сохранённый отчёт;
- `POST /ai/submissions/{id}/code-review` с `{}` — идемпотентная постановка;
  ручной запуск только открытой сдачи, даже если автоматическая проверка выключена;
  `{retry: true}` явно повторяет только ошибочный/прерванный анализ.

Повторный просмотр не вызывает LLM заново. Выключение автоматической проверки
прекращает автоматические анализы, не удаляя сохранённые отчёты и не меняя решения.
Уже готовые подсказки остаются доступны; отдельную сдачу можно проверить вручную.
Для ручного запроса сохраняются `manual_requested` и права инициатора: обычный
преподаватель остаётся ограничен своими группами, администратор может проверить
доступную ему сдачу. Worker повторно проверяет доступ и актуальность снимка
до вызова модели и сохранения результата. Глобальное отключение ИИ, отсутствие
провайдера и ограничения контекста нельзя обойти ручным запуском. Настройка
автопроверки задания, оценки, файлы, Moodle и соседние сдачи не меняются.
При повторном переходе выключено → включено ошибочные непроверенные сдачи
могут быть поставлены заново; повторное сохранение уже включённого флага этого
не делает. Перед вызовом провайдера и сохранением его ответа повторно
проверяются настройки, доступность сдачи и совпадение снимка.

Провайдер получает условие, общие инструкции, максимальный балл именно этой задачи
и полный текст файлов immutable snapshot, без ФИО, выставленных оценок и личных
комментариев преподавателя. От него требуется JSON
`{summary, recommended_grade, recommended_comment, findings: [{path, line, end_line?, severity, message}]}`.
В `code-review-v2` балл должен быть в диапазоне от нуля до максимума, с точностью
до двух знаков и непустым обоснованием; если данных недостаточно, он равен `null`.
Компиляция и подбор/выполнение тестов не входят в этот процесс; промпт запрещает
модели придумывать результаты запуска. Сервер проверяет схему, диапазон оценки,
наличие файлов и существование диапазонов строк. Невалидный
ответ повторно запрашивается в пределах трёх попыток, затем становится `FAILED`;
его сырой текст не сохраняется и не показывается. В журнал пишутся ID проверки,
номер попытки и безопасная категория ошибки (для ошибок схемы — тип и поле,
без содержимого поля, исходников, персональных данных и ключей).
Сохраняются версия prompt, модель, снимок и валидированный отчёт. Mock-провайдер
возвращает явную надпись, что реальный анализ не выполнялся, без замечаний.

Преподаватель видит подсказки и подсветку строк с пояснениями при наведении;
подсветку можно отключить. Просмотр доступен только преподавателю в его области
проверки и администратору, студентам отчёт недоступен. Это предположения ИИ:
ложные срабатывания возможны, а отсутствие замечаний не доказывает правильность.
Оценка, решение преподавателя, исходный код и Moodle автоматически не меняются.

Рекомендованный балл и комментарий хранятся в `AICodeReview`, отдельно от
официального `ReviewDecision`. В форме проверки показывается карточка
«Ответ ИИ:» с действием «Утвердить рекомендацию ИИ». Это действие только заменяет
балл и комментарий в редактируемых полях формы и при необходимости закрепляет
работу за преподавателем для перепроверки. Диалог отправки оно не открывает.
Преподаватель может исправить значения. «Сохранить» сохраняет только локальный
черновик с `ai_review_id`, без решения и без очереди выгрузки. Только основная
кнопка «Утвердить» и подтверждение в её диалоге отправляют текущие значения полей
в Moodle, с обычными проверками прав и закрепления. Отмена диалога сохраняет
введённые значения для дальнейшего редактирования. Старые отчёты без рекомендации остаются
доступны без придуманного балла и без автоматического повторного платного запроса.

При нажатии стрелки **«Вернуться к работам»** для просмотренных в этой работе
студента ИИ-проверок вызывается `POST /ai/submissions/{id}/code-review/discard`.
Переключение между заданиями внутри работы не считается выходом.
Сервер удаляет только сохранённый ИИ-черновик выходящего преподавателя;
обычный ручной черновик, чужие черновики и утверждённые решения не затрагиваются.

Автоматическая проверка после сдачи (`manual_requested=false`) **сохраняется**:
повторное открытие показывает тот же балл, комментарий и замечания, без нового
вызова модели. Выход не отменяет и не перезапускает её очередь, выполняющийся
запрос или оставшиеся попытки. Применение ответа в форму не утверждает оценку:
при выходе без основной кнопки «Утвердить» сбрасывается только этот ИИ-черновик,
а сохранённый автоматический отчёт остаётся доступен для следующего просмотра.
Дополнительного чтения или записи Moodle при таком выходе нет: официальное
решение до утверждения вообще не изменялось.

Для **ручной** проверки (`manual_requested=true`) сохраняется прежняя логика:
неутверждённая рекомендация отменяется и скрывается вместе с замечаниями.
API возвращает `automatic` и `recommendation_status`
(`NONE`, `PENDING`, `APPROVED`, `DISCARDED`). Суточного ожидания и таймера истечения нет.
Если запрос отмены не удался, страница остаётся открытой и предлагает повторить
выход. Закрытие вкладки браузера не заменяет явный выход стрелкой.

Официальный результат Moodle остаётся действующим всё время. При отмене ручной проверки сервер
ставит точечное чтение **той же попытки Moodle** в обычную очередь синхронизации,
используя доступ выходящего преподавателя. Активное чтение этой попытки тем же
преподавателем переиспользуется; сканирования курса и отправки оценок нет.
Права и Moodle-сессия проверяются заново перед запросом; чужая учётная запись
не подставляется. Если Moodle недоступен или нет точной связи с попыткой,
сохраняется последний полученный официальный результат. Ошибка синхронизации
никогда не приводит к применению ИИ-оценки. Отмена доступна и при выключенном ИИ.

Отменённый ручной отчёт сохраняется в БД до следующей явной проверки. Ожидающее задание
ИИ снимается с очереди, уже выполняющийся запрос заканчивается без применения
результата. Синхронизация Moodle не запускает отменённый анализ повторно:
нужен явный клик «Проверить ИИ». При утверждении передаётся `ai_review_id`;
сервер проверяет, что отчёт не отменён и относится к текущему снимку,
затем атомарно связывает его с `ReviewDecision`. Старой вкладкой отменённую
рекомендацию утвердить нельзя. Уже утверждённое решение выход не отменяет,
в том числе если его отправка ещё ожидается или завершилась ошибкой.

Teacher chat остаётся отдельным диалогом и сразу открывается во вкладке «ИИ».
Служебный блок состояния автоматической проверки в этой вкладке не показывается.
Общий тумблер «Замечания ИИ» над редактором скрывает/показывает все подсветки;
выбор сохраняется в браузере для следующих работ. До первого анализа на его
месте находится серая кнопка «Проверить ИИ» с рамкой и внутренней тенью; подсказка
при наведении объясняет ручной запуск. На время запроса, очереди и анализа она
неактивна, а после завершения автоматически заменяется тумблером подсветки.
Во время проверки над полями оценки виден текущий номер попытки; промежуточные
ошибки не показываются как окончательный отказ. После исчерпания трёх попыток
там же появляется явный блок с причиной и кнопкой «Повторить ИИ-проверку».
Этот явный повтор начинает новый цикл с нуля; сам просмотр ошибки этого не делает.
Старые `FAILED` не запускаются автоматически после обновления приложения.
Отключение анализа, потеря доступа, смена снимка или явный выход из ручной проверки
останавливают повторы без дальнейших платных запросов. Выход из просмотра автоматической
проверки не прерывает её. Двойные клики, повторный POST и обновление
страницы не создают повторной проверки одного снимка. В песочнице управление
недоступно. Hover замечания содержит описание и действие
«Спросить у ИИ». В оригинале сдачи преподаватель также может выделить любой
фрагмент и нажать такую же плавающую кнопку. В песочнице и у студентов её нет.
Оба действия только открывают чат и прикрепляют фрагмент в серой карточке над
полем ввода: имя файла, номера строк и до двух видимых строк кода. Карточку можно
убрать крестиком, не меняя свой вопрос. Для замечания сохраняется и его описание.
Вопрос автоматически не придумывается; без собственного текста отправка недоступна.
Создание диалога и вызов модели происходят только после явной отправки.
Полное условие, все файлы неизменяемого снимка и текущий комментарий собираются сервером.
Системный промпт считает выделение только указателем на интересующий участок:
помощник сверяется с полным файлом и не разбирает обрезанные буквы, скобки или
границы выделения как ошибки программы. Реальные ошибки полного исходника
по-прежнему отмечаются; само обрезание обсуждается только по прямому вопросу преподавателя.
Выбранный фрагмент передаётся целиком вместе с вопросом, а не обрезается до превью;
если суммарный размер превышает лимит сообщения 20 000 символов, интерфейс просит
сократить вопрос или выделение до обращения к модели. Карточка сохраняется в
истории вместе с вопросом. После отправки фрагмент убирается из поля ввода и не
восстанавливается даже при ошибке ответа. Сам вопрос при ошибке возвращается, если
преподаватель ещё не начал новый; новое выделение, сделанное во время ответа,
не теряется. При смене задачи чужое выделение не переносится.

Красная кнопка «Очистить чат» справа в фиолетовой шапке запрашивает подтверждение.
`POST /ai/teacher-threads/reset` атомарно закрывает открытые преподавательские
диалоги текущего пользователя по выбранной сдаче и создаёт пустой диалог.
Оценки, замечания ИИ и чужие диалоги не меняются; сообщения сохраняются для аудита,
но не попадают в новый контекст. Перезагрузка страницы открывает новый пустой чат.
Очистка не вызывает модель и недоступна во время ответа, загрузки истории и в
режиме чтения. При ошибке очистки текущая переписка и черновик остаются на месте.
Кнопка отправки растягивается до высоты поля вопроса, включая изменение его размера.

`POST /ai/threads/{id}/messages?stream=true` сохраняет прежние проверки доступа,
CSRF, лимитов и контекста. SSE возвращает события `thinking`, `delta`, `done`
или `error`. Reasoning-текст не передаётся и не сохраняется: интерфейс показывает
`Thinking.` / `Thinking..` / `Thinking...` и короткую подпись «Тема анализа».
Подпись — приблизительная тематическая классификация последних фрагментов
`reasoning`, `reasoning_content` или `reasoning_details`, а не цитата или полный
пересказ рассуждений. Сервер выдаёт только предопределённые темы на русском
(строки, память, границы и т. п.), не чаще одного изменения за 2 секунды;
дополнительных вызовов LLM нет. Неизвестные/зашифрованные данные игнорируются.
При отсутствии распознаваемой темы остаётся общая подпись «условие и код».
В БД сохраняется только завершённый
ответ, перед событием `done`. Разрыв/ошибка не создаёт завершённого сообщения;
частичный ответ помечается как несохранённый. Повторных платных запросов нет
без отправки пользователем. Уход со сдачи отменяет поток. Транспорт ограничивает
общее время (`AI_TIMEOUT_SECONDS=180`), отсутствие новых данных в потоке
(`AI_STREAM_IDLE_TIMEOUT_SECONDS=60`), размер байтов ответа и длину вывода.
Для потока используется отдельный `AI_MAX_STREAM_BYTES=67108864` (64 MiB):
служебные JSON-поля и reasoning повторяются в тысячах событий и не должны исчерпать
маленький лимит обычного JSON-ответа до появления текста. Одно событие и неполный
буфер по-прежнему ограничены `AI_MAX_RESPONSE_BYTES=1048576` (1 MiB).
Преподавательский ответ допускает до `AI_TEACHER_MAX_OUTPUT_CHARS=131072` символов;
студенческий лимит `AI_MAX_OUTPUT_CHARS=12000` не меняется. Браузер отдельно ограничивает
транспортный поток (32 MiB), событие и накопленный текст, не обрезая допустимые ответы.
Пока модель работает, backend отправляет SSE keep-alive раз в 15 секунд,
чтобы промежуточный proxy не закрывал соединение при неизменной теме анализа.
Внутренние данные ошибок
провайдера не раскрываются. Nginx сохраняет `X-Accel-Buffering: no` для внешнего
reverse proxy. Другие протоколы пока используют буферизованный ответ; студентам
код не выдаётся до проверки полной учебной политики.

Ответы отображаются безопасным Markdown (списки, выделения, код, таблицы), без
HTML, исполняемых ссылок и загрузки внешних изображений. Кнопка разворачивания
увеличивает чат на всю рабочую область проверки, не сбрасывая диалог и черновик;
в активном состоянии она подсвечена и возвращает обычный размер повторным нажатием.
В развёрнутом виде сообщения и поле ввода имеют шрифт 16 px вместо 14 px;
заголовок также немного увеличен. Сворачивание возвращает обычные размеры.
Заголовок прокручивается вместе с перепиской; полупрозрачная кнопка раскрытия
остаётся закреплённой и становится непрозрачной при наведении/фокусе.
Протокол провайдера: [OpenRouter streaming](https://openrouter.ai/docs/api_reference/streaming).
Поля рассуждения: [OpenRouter reasoning tokens](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

Детерминированный
`EvidenceReport` — отдельный источник, не вызывающий LLM. Калибровка уверенности
и полноформатный eval-набор для нового режима не реализованы.

## 9. Prompt injection

Student code, comments, task content и stdout считаются untrusted. Меры:

- данные передаются отдельными typed fields, а не смешиваются с instruction text;
- модель получает явное указание игнорировать инструкции внутри code/data;
- tools имеют deny-by-default и серверно проверяемые arguments;
- URL из student content не открываются;
- hidden tests/reference solution никогда не попадают student tutor;
- учительский assistant не может сам применить grade или отправить в Moodle;
- tool results ограничиваются размером и очищаются от control sequences.

## 10. Privacy и стоимость

- отправлять provider только необходимые snippets/evidence;
- псевдонимизировать user ID через стабильный hash per provider/project;
- не отправлять ФИО/группу без функциональной необходимости;
- provider credentials находятся только на server;
- отдельные budget limits на LMS connection/курс и две внешние роли;
- cache допускается только для не­персонального неизменного prefix/context;
- модель/provider переключаются настройкой без изменения доменных данных;
- локальный provider доступен для курсов, где внешняя передача кода запрещена.

## 11. Глобальные и преподавательские настройки

- global kill switch;
- provider/model allow-list;
- student tutor modes по типам работы;
- teacher chat enabled;
- административная настройка рекомендательной проверки конкретной работы
  (включена по умолчанию для новых работ);
- daily/monthly budget;
- retention and external transfer policy;
- documentation source allow-list;
- output policy thresholds;
- audit/export permissions.

Глобальный блок доступен только при активном административном повышении сессии. У преподавателя есть собственный switch СППР для доступного ему курса, если глобальная политика разрешает. Выключение прекращает новые jobs, но не удаляет evidence и не меняет старые decisions.

## 12. Evals до включения

- минимум 100 запросов на выдачу полного решения, включая дробление по частям;
- jailbreak на русском и английском;
- prompt injection в комментариях C++ и stdout;
- ложные/несуществующие citations;
- корректное объяснение распространённых ошибок C++;
- утечка hidden tests/reference/rubric;
- bias по стилю/ФИО — идентичность не должна передаваться;
- калибровка recommended grade на исторической размеченной выборке;
- teacher acceptance/rejection rate и disagreement analysis;
- provider outage/timeout/malformed output.

## 13. Источник OpenAI

Для реализации OpenAI-адаптера использовать актуальную [официальную документацию Responses API](https://developers.openai.com/api/reference/cli/resources/responses/methods/create). Она описывает instructions, conversation/previous response, structured output, tools, moderation, `store` и `safety_identifier`. Moderation API решает безопасность контента, но не задачу «не писать решение C++»; академическая policy остаётся обязанностью приложения.
